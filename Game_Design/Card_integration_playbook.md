# Card integration playbook (YgoDuelist)

Where card-specific behavior should live, and how Harmony patches should delegate.

## Virtual methods on a card base

Use when **every** card of that lineage might override behavior, and the engine calls **one** method on the model.

- **Examples:** `BaseMonsterCard.OnSummoned` / `OnAfterSummonPipelineAsync` (summon effects); `AbstractMonsterCard` pet/stance/flip hooks; `YgoDuelistCard.GetNHandPlayPhaseHighlightModulateOverride` (play-phase hand outline); `YgoDuelistCard.RefineIsValidTarget` (narrow `CardModel.IsValidTarget` after vanilla).
- **Caller:** Services or patches call the virtual once; **no** `if (model is Some_Card)` in the patch.

## Small interfaces (`IYgo…`)

Use when behavior is **optional** or a **capability** shared across unrelated bases (e.g. `MonsterCommandCard` is not a `YgoDuelistCard`).

- **Examples:** `IYgoPrePlayCancelableGridSelection`, `IYgoPlayCardActionPreSpendResourceFlow`, `IYgoTurnStartAtkGrowthFromFieldMonsterAfterCommandReset`, `IYgoPetDebuffPowerAmountReceivedHook`, `IYgoCardZoneRightClick`, `IYgoAfterDuelMonsterDiedZoneCard`, `IYgoNHandPlayPhaseHighlightOverride`.
- **Patch pattern:** `if (model is IYgoSomething x) { x.Method(...); }` — **one** interface check, not one check per card type.
- **Good fit:** graveyard-entry rules like `IYgoOnAddedToYgoGraveyardPile` when the behavior belongs to one card but the timing/owner resolution is shared.

## Domain services

Use for **orchestration** (fusion selection, pile moves, grids) that many cards share. Card classes should **call** services or implement **thin** hooks that call services — avoid duplicating full rules in patches.

For **multiplayer-stable** “which pet?” / “which zone card when several match?” logic, call **`YgoMpCombatOrder`** (`FirstPetWhere`, **`PetsAny`** for existence checks, **`PetsSnapshotAliveDuelMonstersOrderedByCombatId`** for “all live duel field pets” kill/damage passes, `PetsSnapshotOrderedByCombatId` for `foreach` **and** for old `Pets.ToList()` combat snapshots, `CreatureListOrderedByCombatId` for tribute material lists (including **`pending.Pets[0]`**-style “first” material), `FirstCardWhereStable`, …) instead of raw `Pets.FirstOrDefault`, **`Pets.Any` on live `PlayerCombatState.Pets`**, **`foreach` on live `PlayerCombatState.Pets`**, `foreach` on **`Pets.OrderBy(CombatId)`** (still live under the enumerator), ad-hoc `Pets.ToList()` without `CombatId` order, **multi-line** `.Pets` / `.FirstOrDefault` chains, or `zone.Cards.FirstOrDefault` — see `Game_Design/Multiplayer_playbook.md` (“Shared conventions and helpers”). `YgoMpCombatOrder` itself should remain snapshot-first internally so wrappers like `FirstPetWhere` / `PetsAny` cannot regress to live-list iteration by accident. For Hook postfixes that require async combat work, use `void` postfix + **`TaskHelper.RunSafely`** dispatch to a private async method (never mutate combat state directly from `async void`). That includes **monster command** pet resolution (`Command_Attack`, `Command_Defend`, `Command_Change_Battle_Position`) and **`MonsterActivatedEffectRuntime.FindPetForSourceMonster`**: use **`FirstPetWhere`**, not a hand-rolled `OrderBy(CombatId).FirstOrDefault` or bare `Pets.FirstOrDefault`. Owner / pet **self-damage that is a cost, not a powered hit** should use **`ValueProp.Move | ValueProp.Unpowered`** on `CreatureCmd.Damage` where applicable (see playbook + `Needle_Ball`).
For top-of-draw effects (mill / banish top deck), prefer explicit index semantics (`draw.Cards[0]` with `Count > 0`) instead of `draw.Cards.FirstOrDefault()`: this keeps behavior as pile-order “top card” while keeping MP grep passes focused on true unstable “pick one among many” cases.
For RNG-tier substitutions or weighted picks (e.g. starter-grid catalog lists), sort tie-lists to a stable key before `UnstableShuffle` / random selection so shuffle inputs are deterministic across peers. Apply the same rule to direct `NextInt` index picks: stable-sort candidate pools/tie-lists first, then pick.
For combat registries backed by `Dictionary`/`HashSet` (equip/link maps, payload maps), avoid direct key enumeration in gameplay/reconcile paths; snapshot and stable-order keys first (e.g. `YgoMpCombatOrder.CardsOrderedForMp`) before detach/rebind loops.
When carrying combat-id keyed aggregates (`Dictionary<uint, ...>`) across phases (record -> consume -> apply), copy/iterate them in ascending key order before consumption to avoid hash-order drift in downstream action sequencing.
When gameplay/reconcile logic fans out over all combat players, iterate `runState.Players` / `cs.Players` through `YgoMpCombatOrder.PlayersSnapshotOrderedByNetId(...)` instead of raw list order to keep owner-wide passes deterministic across peers.
For spell/trap zone source resolution in recurring combat effects (field powers, graveyard triggers, periodic ticks), do not use raw `zone.Cards.OfType<...>().FirstOrDefault(...)`; use `YgoMpCombatOrder.FirstCardWhereStable(zone.Cards, predicate)` so the chosen source card is deterministic when multiple matches exist.
Apply the same deterministic selection rule to extra-deck typed summon target resolution in command cards (`Special_Summon_*` flows): use `YgoMpCombatOrder.FirstCardWhereStable(extra.Cards, predicate)` rather than ad-hoc `extra.Cards.OfType<T>().FirstOrDefault()`.
Do not introduce local one-off order rules for “first active” card selection (for example `OrderBy(Id.Entry).FirstOrDefault` in a single service). Route those through `YgoMpCombatOrder.FirstCardWhereStable(...)` so selection semantics stay centralized and consistent.
For fallback enemy/card picks that currently use `OrderBy(...).First()` in card logic, prefer existing shared helpers (`YgoMpCombatOrder.CreatureListOrderedByCombatId`, `FirstCardWhereStable`, etc.) over per-file ordered-first chains.
For combat-id keyed creature lookup outside `PlayerCombatState.Pets`, use `YgoMpCombatOrder.FindCreatureByCombatId(...)` instead of ad-hoc `cs.Creatures.FirstOrDefault(c => c.CombatId == ...)`.
For all-enemy effect passes (including recurring field-power ticks, mass-damage spells, and Slifer-style passes), do not hand-roll `cs.HittableEnemies.Where(e => e.IsAlive)` / `.ToList()` in each file; use `YgoMpCombatOrder.HittableEnemiesAliveOrderedByCombatId(cs)` so alive enemy snapshots and ordering are shared and deterministic. For passes that must include dead enemies too (checksum power cleanup, etc.), materialize with `YgoMpCombatOrder.CreatureListOrderedByCombatId(cs.HittableEnemies)` instead of raw `HittableEnemies.ToList()` / `foreach` over the live list. Use the same helpers when the loop variable is **`var`** (`foreach (var enemy in ...HittableEnemies)`): rewrite to **`foreach (Creature enemy in YgoMpCombatOrder.HittableEnemiesAliveOrderedByCombatId(...))`** so automated greps and human review see one pattern. When building filtered enemy lists (e.g. “enemies with attack intent”), start from **`HittableEnemiesAliveOrderedByCombatId`** then apply predicates — do not chain `.Where` directly off **`cs.HittableEnemies`**.
For deterministic RNG targeting over alive enemies, do not build candidate pools with per-file `YgoDeterministicRng.StableOrder(cs.HittableEnemies.Where(...), ...)`; build the pool through `YgoMpCombatOrder.HittableEnemiesAliveOrderedByCombatId(cs)` first, then call `PickOne(...)`.
For deterministic RNG over card pools (hand/zone/other card lists), build candidate pools through `YgoMpCombatOrder.CardsSnapshotOrderedForMp(...)` before `PickOne(...)` rather than raw `.ToList()` snapshots. Use the same helper for **`CardSelectCmd.FromSimpleGrid`** candidate lists and for **bulk `CardPileCmd.Add(...)`** snapshots when order can affect MP parity (e.g. `Card_Trader`, `The_Law_of_the_Normal`, GY selection on `Keldo` / `Des_Feral_Imp`, Daedalus lines sending hand+STZ to graveyard).
For combat-path **preview / confirmation-only** grids (manual confirm with `MinSelect = MaxSelect = 0`), do not call raw **`CardSelectCmd.FromSimpleGrid(...)`**. Use **`YgoPreviewGridSelection.ShowPreviewAsync(...)`** so the prompt still consumes a synchronized choice id and stale buffered `Index` results cannot leak into later actions (Graceful Dice / coin-flip preview class).
For combat-path **ordinary card-list picks** from piles (deck / graveyard / hand / banished) — including singleton “activate this card?” prompts when the card is represented as a normal `CardModel` row — do not use raw **`CardSelectCmd.FromSimpleGrid(...)`**. Collect candidates through **`YgoMpCombatOrder.CardsSnapshotOrderedForMp(...)`** and route the selection through **`TributeSummonGridSelect.FromSimpleGridCombat(...)`** with a rebuild callback so MP observers resolve the same combat-card identities after any intervening state change.
Apply the same rule to **pre-play cancelable** search / recovery grids (`IYgoPrePlayCancelableGridSelection`) when the selectable rows come from deck / graveyard / discard / extra-deck piles: build the candidate list through **`YgoMpCombatOrder.CardsSnapshotOrderedForMp(...)`**, use **`TributeSummonGridSelect.FromSimpleGridCombat(...)`**, and resolve the chosen card with **`YgoMpCombatOrder.FirstCardWhereStable(...)`** instead of `selected.FirstOrDefault()`.
When many cards share the same selection plumbing, move that plumbing into a shared helper instead of repeating it in each card. Current green helpers:
`YgoCardGridChoice.TryChooseSingleAsync(...)` for synced choose-one combat grids,
`YgoPrePlayGridSelection.TryPrepareSingleCardPayloadAsync(...)` / `TryPrepareSingleOptionIdPayloadAsync(...)` for `IYgoPrePlayCancelableGridSelection`,
and `YgoActivatedEffectTributeSelection.TryPrepareSingleTributeAsync(...)` for common activated-effect tribute preselection. Cards should still own candidate construction and the meaning of the payload.
For choose-one combat grids over ordinary card rows, prefer `YgoCardGridChoice.TryChooseSingleAsync(...)` even when the old code "works": do not repeat local `try/catch OperationCanceledException`, `CardSelectCmd.FromSimpleGrid(...)`, and `FirstOrDefault()` extraction in each card/service. Keep only the candidate builder and the card rule outcome in the caller.
For multi-pick combat grids over draw / discard / graveyard / hand card rows, route through `TributeSummonGridSelect.FromSimpleGridCombat(...)` with a canonical rebuild callback instead of raw `CardSelectCmd.FromSimpleGrid(...)`. The shared helper owns wire format; the card/service owns min/max counts and post-pick meaning.
Prefer the narrower shared helper when one already matches the selection family instead of open-coding one more `FromSimpleGrid` flow: `YgoHandCardSelection` for choose-one hand costs, `YgoFusionExtraDeckSelection` for direct extra-deck fusion picks, `YgoCreatureProxySelection` for `YgoEnemyIntentProxyCard` rows, and `YgoActivatedEffectTributeSelection` for activated-effect tribute preselection.
If the caller only rebuilds an already-ordered combat-card list and interprets the chosen result, prefer `YgoOrderedCardSelection` over direct `YgoCardGridChoice` / `TributeSummonGridSelect` usage. Keep `YgoCardGridChoice` for cases that already have the canonical combat-card list in hand.
For non-combat / run-state simple-grid flows (reward splitting, Neow starter draft, relic/card-option browse, campfire deck-edit grids), prefer `YgoSimpleGridSelection` instead of repeating `new BlockingPlayerChoiceContext()` + `CardSelectCmd.FromSimpleGrid(...)` + local cancel plumbing in each service or patch.
For run-state/rest-site selectors that wrap vanilla deck selection screens, verify the emitted multiplayer result type. `NDeckUpgradeSelectScreen` can emit `DeckCard` wire even when a YGO wrapper also syncs indexes for mixed deck + extra-deck candidates; callers should either avoid double-syncing or explicitly tolerate/log `DeckCard` fallback like `YgoSmithRestSiteOptionPatch`.
Within a card or service, prefer one canonical local `Build*Candidates` / `Build*Targets` helper reused by availability checks, preplay selection, and resolution revalidation instead of re-expressing the same filters inline three different ways. That keeps card-owned rules local while making future MP grep passes mechanical.
Apply that same rule to activated effects and summon/flip triggers too, not just preplay flows: if a card checks a graveyard/deck/field pool in `IsActivatedEffectAvailable`, then uses the same pool for `YgoOrderedCardSelection`, the filter should live in one local helper on the card.
If the prompt is just "do you want to activate this exact card/effect instance?", do not rebuild one-element candidate lists inline in each card/service. Route that through `YgoOrderedCardSelection.TryConfirmSingleCardAsync(...)` so singleton activation prompts stay grep-friendly and use the same synced ordered-grid contract as broader selectors.
For player-owned singleton relic access (`GraveyardRelic`, `BanishedRelic`, `ExtraDeckRelic`) that would otherwise repeat `player.Relics.OfType<T>().FirstOrDefault()`, prefer `YgoPlayerRelicAccess.GetRelic<T>(player)` so typed relic ownership lookups stay centralized and grep-friendly.
For repeated player pile lookups (`PileType.Hand.GetPile(player)`, `PileType.Draw.GetPile(player)`, `PileType.Discard.GetPile(player)`, `GraveyardPile.CustomType.GetPile(player)`, `SpellTrapZonePile.CustomType.GetPile(player)`, `YgoCardOptionPile.CustomType.GetPile(player)`, etc.), prefer `YgoPlayerPiles` so cards, services, powers, and patches all share one access layer instead of re-spelling pile ownership in every file.
Apply the same accessor rule to the other owned YGO piles too (`ExtraDeck`, `Banished`, `MonsterZone`, `Field`, `OptionPile`): if a card/service/net helper only needs the owner's pile object or cards from it, route through `YgoPlayerPiles` instead of repeating raw custom-pile `GetPile(player)` calls.
For repeated run-state trunk / side / extra-deck lookups (`PlayerRunTrunk.GetOrCreatePile(player)`, `PlayerRunSideDeck.GetOrCreatePile(player)`, `PlayerRunExtraDeck.GetOrCreatePile(player)` / `GetPileIfExists` / `IsYgoDuelistPlayer`), prefer `YgoPlayerRunPiles` so non-combat UI, rewards, relics, save/load, and merchant/rest-site flows share one ownership contract.
For card-owned candidate builders that just gather ordered cards from a few owner piles before filtering to a card type, prefer `YgoPlayerPiles.OrderedCardsOfTypeFromPiles(...)` and `HasOtherHandCard(...)` instead of re-implementing `Append(PileType.Hand.GetPile(...))` / `Cards.Any(c => !ReferenceEquals(c, this))` in every card. Keep the effect rule and the chosen types on the card.
For graveyard ownership and membership reads, prefer `YgoPlayerPiles.Graveyard(...)`, `GraveyardCards(...)`, and `GraveyardContains(...)` over mixing `GraveyardRelic.GetGraveyardCards(...)`, `GetGraveyardPile(...)`, and raw `GraveyardPile.CustomType.GetPile(...)` at each callsite. Use the relic for relic behavior; use the pile helper for ordinary card/service ownership reads.
Apply that same accessor rule to ordinary owner hand / draw / discard / spell-trap-zone reads too: if a card/service just needs the owner pile object or cards/counts from it, route through `YgoPlayerPiles.Hand/Draw/Discard/SpellTrapZone(...)` instead of open-coding `PileType.*.GetPile(...)` in each file.
For field-monster registry reads, prefer shared `DuelMonsterFieldRegistry` helpers (`OrderedFieldMonsters(...)`, `ContainsFieldMonster(...)`) over repeating `GetFieldMonsters(...).ToList()`, direct `Contains(...)`, or raw `foreach` scans in each caller. Keep the effect rule local; centralize the field snapshot/ordering contract.
For pet-to-source-card binding reads, prefer `DuelMonsterFieldRegistry.HasSourceCard(...)` and `GetSourceMonster<T>(...)` over direct `GetSourceCardForPet(...) == ...`, `ReferenceEquals(...)`, or local cast chains in each caller. Keep the card rule local; centralize the pet/source binding contract.
For powers that live on duel monster pets, do not gate turn hooks on `Owner.Player` alone. Resolve ownership from the registered source monster first (`DuelMonsterFieldRegistry.GetSourceMonster<BaseMonsterCard>(Owner)?.Owner`), then fall back to `Owner.PetOwner` / `Owner.Player`, because pet-bound powers can have a null or unreliable `Owner.Player`. `PumpkingRitualPower` / `NecroticRitualPower` are the reference pattern.
For checksum-only cosmetic power reconciliation, do not use `PowerModel.ApplyInternal` if the power exists only to stabilize serialized marker state and an internal-list path is available. `ApplyInternal` can instantiate combat UI (`NPower`) and load icon resources during `NetFullCombatState.FromRun`, producing noisy or timing-sensitive resource errors on observers. `Creature.Powers` is public read-only and `PowerModel.Owner` is read-only, so checksum-only marker code must go through guarded internal mutable-list / owner-field accessors and fall back to `ApplyInternal`/`RemoveInternal` if the engine fields cannot be resolved; normal gameplay should still use `PowerCmd`.
For singleton pet markers, never rely on `GetPower<T>()` before re-applying: it only finds one copy, so stale duplicates survive. Stance sync must remove every `AttackPositionPower`, `DefensePositionPower`, and `FaceDownStancePower` copy before adding the one authoritative marker from the source card; Attack and Defense are a mutually exclusive group. Checksum reconcile also strips duplicate non-instanced YGO `Single` / `None` powers so markers such as Ra Doomed, Stiff, Fatigue, and stance icons cannot multiply.
When creating checksum-only mutable powers by hand, set the owner backing field before calling `PowerModel.SetAmount(...)`; the engine amount setter can dereference owner state for hover/power bookkeeping. If owner or mutable-list access cannot be resolved, fall back to `ApplyInternal` rather than adding a half-initialized power that later crashes hover tips.
When removing a duel monster pet outside ordinary summon layout, refresh both visual position and sibling draw order after the node leaves `NCombatRoom`: call the shared draw-order/layout refresh from death, banish-release, and hand-release paths. `NCombatRoom.PositionPlayersAndPets` only reruns automatically on initial layout/add; dead pets do not reshuffle the remaining duel monsters by themselves.
For face-down duel monsters that reveal because of a shared combat hook, separate the deterministic state change from optional effect activation. Flip the card face-up and sync stance/keywords immediately on every peer, then use the synced prompt only to decide which `IMonsterFlipEffect.OnFlippedFaceUpAsync` bodies run. `FlipFaceDownMonstersOnPlayerEnemyAttackPatch` + `YgoMonsterFlipEffectRunner.MarkFlippedFaceUpOnField` are the reference pattern; do not leave `FaceDown` mutation behind an async prompt result that can complete on different sides of a checksum. For "select flip effect monsters to activate" prompts, aggregate same-frame candidates before opening the grid, use `MinSelect = 1` + `RequireManualConfirmation = true`, and keep `Cancelable = true` so confirm cannot accidentally submit zero cards while cancel still intentionally skips activation.
For synced combat-grid callers whose only custom logic is “rebuild the ordered candidates and interpret the picked cards,” prefer `YgoOrderedCardSelection.TryChooseSingleAsync(...)` / `TryChooseManyAsync(...)` instead of repeating `TributeSummonGridSelect.FromSimpleGridCombat(...)` plus the same rebuild lambda and typed extraction in each card or service.
For synced grid / selection-return enumerables of cards, do not end pipelines in `....OfType<T>().FirstOrDefault()` when more than one element can satisfy the type filter; resolve the typed pick with `YgoMpCombatOrder.FirstCardWhereStable(..., c => c is T) as T` so host/client agree on tie order (same contract as zone/extra-deck “pick one” cases).
For vanilla card selectors used by potions, relics, powers, or external mods, rely on the central MP expectation patch rather than local wrappers. Combat hand selectors (`CardSelectCmd.FromHand` / `FromHandForUpgrade`) sync `CombatCard` wire, simple/choose grids sync `Index` wire, and deck selectors sync `DeckCard` wire. `CardSelectCmdVanillaHandChoiceExpectationPatch` registers the expected wire type around the vanilla wait so stale buffered choices of another type are rejected before vanilla calls `AsCombatCards()`, `AsIndexes()`, or `AsDeckCards()`.
For custom code that calls `PlayerChoiceSynchronizer.ReserveChoiceId` / `WaitForRemoteChoice` directly, push a `GridCombatMpExpectation.Active` scope before reserving the id and dispose it after the wait. Declare every accepted wire shape (`AllowIndex`, `AllowCombatCard`, `AllowDeckCard`, etc.) and the candidate row bounds. Do not leave a raw direct wait with no expectation guard.
When many monsters share the same summon/flip wrapper shape (`await base.OnSummoned`, normal/tribute gate, `choiceContext ?? new BlockingPlayerChoiceContext()`), put that plumbing on `BaseMonsterCard` and keep only the per-card effect body in the card. Do not create a named service just to hold that wrapper boilerplate.
Likewise, repeated “upgraded or upgrade-preview” UI checks should use the shared card property instead of re-spelling `IsUpgraded || UpgradePreviewType != ...` in every file.
When cards/services just need a blocking choice context, do not open-code `new BlockingPlayerChoiceContext()` or `choiceContext ?? new BlockingPlayerChoiceContext()` everywhere. Use `YgoChoiceContexts.Blocking(...)` so that context creation stays grep-friendly and centralized.
For graveyard-triggered “activate this exact source card, then continue” flows, use `YgoGraveyardTriggeredActivation.TryConfirmSourceAsync(...)` instead of repeating the same `CardSelectorPrefs` + `TryConfirmSingleCardAsync` boilerplate in every graveyard service.
For per-source temporary debuffs with their own follow-up state, make the power `IsInstanced` and keep the once-per-source latch on the power instance. `Slifer_the_Sky_Dragon` is the reference: each Slifer applies its own Slifer Pressure instance to each enemy, and each pressure instance applies its own once-per-turn Blight when that enemy's attack intent first recalculates to 0.

## Anti-patterns (red)

- Named card types in patches: `if (model is Fusion_Gate)` with multi-step rules.
- Same for Services when the block is really **one card’s rule** — move to that card (virtual or interface).

## Audit folder (optional, at your pace)

`YgoDuelistCode/audit/` may contain a one-time or occasional file list (`all-cs-files.txt`), triage notes (`triage-*.txt`, `triage-tier-summary.md`), and an optional script `Run-CardLogicAudit.ps1` if you ever want to regenerate grep snapshots by hand. **Nothing here is required on build** and you should not maintain an ever-growing automated checklist — refactor card-scoping issues as you go, using the patterns above. Work tracking can live in your Cursor plan todos if you use that workflow.
